# Windows 팀 배포

## 설치와 이전 설치판 전환

Windows 10/11 x64에서 `Folio-win-Setup.exe`를 실행합니다. 0.11.0부터 Velopack을 사용하며 기본 위치는 `%LOCALAPPDATA%\Folio`입니다. 관리자 권한이나 Python이 필요하지 않습니다. 시작 메뉴의 **Folio**로 실행하세요. 앱 본체는 `current/`, 실행을 중계하는 파일과 업데이트 도구는 그 위에 있습니다.

0.10.x 이하의 NSIS 설치판은 자동 업데이트로 전환되지 않습니다. 모든 작업을 저장하고 트레이에서 **완전히 종료**한 다음 Windows에서 기존 Folio/Paperlight를 제거하고 새 설치판을 한 번 설치합니다. 기존 설치 폴더에 직접 넣은 사용자 문서는 먼저 보관하세요. 사용자 설정·서명·복구본의 `%LOCALAPPDATA%\Paperlight\Paperlight` 경로와 Paperlight.PDF 식별자는 유지합니다. 새 설치 뒤 Windows 기본 앱 설정에서 PDF 연결을 확인하세요. UserChoice/Hash는 직접 변경하지 않습니다.

`Folio-0.11.0-Portable.zip`은 이전처럼 폴더 전체를 함께 보관합니다. 포터블과 개발 실행은 업데이트 서버에 연결하지 않습니다. 설치판과 포터블은 같은 Windows 계정의 설정·서명·복구 공간을 공유합니다.

아직 디지털 코드 서명을 하지 않은 빌드입니다. 배포 출처와 `SHA256SUMS.txt`를 확인하세요. 회사 정책이 차단하면 담당자에게 확인하며 보안 프로그램을 끄지 않습니다.

## 자동 업데이트와 제거

설치판은 시작 시 공개 GitHub Releases의 안정 버전을 확인·다운로드합니다. **더보기**에서 업데이트 상태를 확인하고 재시작할 수 있습니다. 다운로드가 끝나면 보이는 창에 재시작 여부를 묻고, 거절하면 나중에 메뉴로 적용합니다. 모든 탭의 미저장 문서·미적용 입력 확인이 끝난 뒤에만 업데이트를 예약합니다. 종료 취소나 업데이트 도구 실행 실패 때는 탭을 보존합니다. 변환 중에는 재시작하지 않습니다. 트레이에 숨긴 창은 자동으로 드러내지 않습니다.

다운로드 크기·해시는 Velopack이 검증합니다. 문서·PDF 경로·서명·설정을 보내지 않으며 업데이트 네트워크 요청만 합니다. 오프라인에서는 편집을 계속하고 메뉴에서 다시 확인합니다. 첫 공개 Release 전에는 받을 업데이트가 없습니다. 비공개 저장소 접근 토큰을 앱에 넣지 않습니다.

Windows **설정 → 앱 → 설치된 앱 → Folio → 제거**를 사용합니다. `%LOCALAPPDATA%\Paperlight\Paperlight`의 서명·복구본·설정은 유지합니다. 설치 폴더는 업데이트 때 교체되며 제거 시 삭제될 수 있으므로 문서를 앱 설치 폴더 안에 저장하지 마세요.

## 개발자 빌드와 게시

Python 3.13 x64, Git, Windows 맑은 고딕, .NET SDK와 `vpk`가 필요합니다. Python 라이브러리와 CLI는 **1.2.161**로 맞춥니다. 일반 사용자 PC에는 SDK가 필요하지 않습니다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
dotnet tool install --global vpk --version 1.2.161
.\.venv\Scripts\python.exe scripts\release.py --bump 0.11.1
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
# 소스를 검토·커밋한 뒤 깨끗한 작업 트리에서
.\.venv\Scripts\python.exe scripts\release.py
# 기존 설치·기본 앱 후보·바로가기가 없는 Windows 계정에서
.\.venv\Scripts\python.exe scripts\verify_installer.py
```

`release.py`는 `build/distribution/Folio`를 새로 만들고 `release/<버전>/`에 설치 EXE, 전체 업데이트 nupkg, `releases.win.json`, 일반 포터블 ZIP, Git HEAD의 Source ZIP, `SHA256SUMS.txt`, 커밋·해시가 든 `release-info.json`을 만듭니다. `dist/Paperlight`는 건드리지 않습니다. 같은 버전의 기존 결과를 덮어쓰지 않습니다. `vpk`의 포터블 출력은 배포에서 제외하고 자동 업데이트하지 않는 일반 폴더 ZIP을 제공합니다. 델타는 사용하지 않습니다.

SDK가 없으면 공식 `vpk.1.2.161.nupkg`의 `tools/net10.0/any/vpk.dll`과 .NET 10 런타임을 사용해 `--vpk <vpk.dll 경로>`를 지정할 수 있습니다.

설치 QA는 기존 설치가 있으면 중단합니다. 검증 전용 한글 경로에 조용히 설치하고 PDF 후보 등록·시작 메뉴·버전·패키지 자체의 편집/복구/탭 시험·제거·사용자 데이터와 UserChoice 보존을 검사합니다. 합성 이벤트 검증이며 실제 사용자 IME 조작 검증과 구분합니다. 0.10.x 이하의 NSIS QA는 해당 버전 소스의 `scripts/verify_installer.py --upgrade-from <이전 Setup.exe>`로 재현합니다.

게시 전 `git fetch --all --tags` 후 `scripts/scan_publication.py --gitleaks <gitleaks.exe>`를 실행합니다. Gitleaks는 전체 refs의 이력을 검사하고, 보완 검사는 커밋 메타데이터·blob·태그·PDF 텍스트의 이메일·휴대폰·주민번호 후보를 검사합니다. 발견되면 공개하지 말고 보고하며, 이미지·개인 이름 등 자동 검사가 다루지 못하는 내용은 별도 검토합니다. 보고서는 `evidence/publication-scan/`에 남깁니다.

**main 병합·푸시와 Release 업로드는 사용자 승인 후에만** 진행합니다. 승인 후 원격 main과 현재 커밋을 일치시키고 `scripts/release.py --publish`로 게시합니다. 자산을 draft에 모두 올린 뒤 공개하므로 불완전한 업로드가 업데이트 피드에 노출되지 않습니다. 업로드 실패 시 남은 draft를 검토·정리하세요. 같은 태그/Release를 덮어쓰지 않습니다. GitHub Actions는 테스트·패키징·설치 QA와 아티팩트만 수행하며 Release를 게시하지 않습니다.

`build/`, `dist/`, `release/`, `evidence/`, 타사 바이너리와 조사 원본은 Git에 넣지 않습니다. 같은 의존성으로 재빌드할 수 있지만 바이트 단위 동일 빌드는 보장하지 않습니다. 외부 배포의 라이선스 범위는 `THIRD_PARTY_NOTICES.md`를 확인하세요.
